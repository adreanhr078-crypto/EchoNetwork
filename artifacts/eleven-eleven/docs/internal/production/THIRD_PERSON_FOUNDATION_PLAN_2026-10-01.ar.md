## 1. القرارات المثبتة

- Godot الحالي هو محرك اللعب؛ Windows والهاتف **Landscape** لهما نظام حركة واحد. الجودة الرسومية تتدرج حسب الجهاز، لكن قواعد التحكم والباركور متساوية.

## 3. ترتيب التنفيذ وبوابات الخروج

### الدفعة A — Controller وحفظ مقدار العصا

1. تسجيل baseline للاعب الحقيقي والافتتاح والصيانة؛ حفظ الفشل إن وجد.
2. إصلاح فقدان مقدار العصا داخل اللاعب الحالي، لا إنشاء controller بديل. توحيد نية move/look/jump/roll/interact عند حدود الإدخال الموجودة.
3. radial deadzone مبدئية15% قابلة للضبط، يعاد توزيع النطاق المتبقي0→1. عتبة Run مبدئية85% للدخول و75% للخروج لمنع التذبذب؛ أرقام ضبط أولي تُراجع بالتجربة، وليست نتائج أداء مثبتة.
4. سرعة تتدرج مع الدفع؛ لا قفزة سرعة عند عتبة Run ولا تعويض لانزلاق الأنيميشن بتغيير مفاتيحه. يحفظ Run حدود stamina الموجودة؛ Roll لا يطلق ركضاً عند الاستمرار.
5. فحص القفز والـair control وlight/heavy landing بحسب سرعة السقوط، مع منع إطلاق الهبوط/القفز مرتين عند انتقال الحالة.

**الخروج:** اختبارات اللاعب داخل Godot تثبت حركة0/جزئية/كاملة واتجاهات قطرية وثبات السرعة عبر yaw الكاميرا؛ عقبة وسقف وميل؛ coyote120ms وbuffer150ms عند حدود الزمن مع سماحية خطوة physics واحدة؛ Roll ثم Jump والإلغاء دون ghost input. أي حركة موجودة غير مقبولة بصرياً تُعزل وتُشخّص وفق Golden، ولا تصبح PASS من نجاح الفيزياء.

### الدفعة B — Camera

- تطوير SpringArm الحالي قبل إدخال أي camera rig آخر. التنعيم بزمن الاستجابة، ويستقل yaw اللاعب عن عون landing/framing. لا تأخر زائد خلف الجسم ولا recoil قوي عند هبوط أو mantle.
- orbit كامل، pitch محدود قابل للاستعمال، sweep يمنع اختراق جدار/زاوية/أرض/سقف، اقتراب آمن عند ضيق المساحة وعودة ناعمة بعد الخروج.
- shoulder/framing خفيف يظهر اليد والحافة وموضع الهبوط، FOV65 مع زيادة قصوى5 درجات عند الحاجة؛ Reduced Motion يحافظ على وضع مستقر.
- فحص حفظ واستعادة pose/FOV/input ownership عند نهاية السينمائي الطبيعية أو skip أو cancel أو scene unload، باستخدام مسار العودة الموجود.

**الخروج:** مشهد Godot فعلي يسجل orbit، ممر ضيق وزاوية وحافة ومصعد؛ لا crossing للمصادم ولا فقد للهدف/مكان الهبوط؛ yaw يظل اتجاه المستخدم بعد ترك الإدخال؛ لا jump لحظي عند climb/vault/landing أو رجوع السينمائي. تسجيل المسار ومراجعته، لا قبول من صور ثابتة فقط.

### الدفعة C — Mobile Controls النهائية

- الواجهة الحالية جزء من الـruntime النهائي، لا mouse-only prototype. العصا يسار وسحب النظر يمين وJump/Roll/Interact حسب السياق. أثناء hang يتاح Drop بوضوح، دون إطلاق Roll أثناء إفلات الجدار.
- ملكية إصبع مستقلة؛ إصبع حركة + إصبع نظر + إصبع قفز/تفاعل. ابتداء اللمس فوق أي UI يمنعه من امتلاك الكاميرا؛ سحب الإصبع عبر UI لا ينقل ملكيته إلى زر آخر.
- إزالة أي ازدواج mouse emulation بطريقة محدودة لا تكسر UI؛ ضغط/إفلات/إلغاء/focus/pause/resize/reorientation لا تترك held states. أحداث اللمس الافتراضية في الاختبار ليست إثبات هاتف.
- حفظ sensitivity وdeadzone والحجم/الشفافية/الموضع، وإعدادات محدودة وآمنة؛ landscape بالجهتين، safe areas والـnotch/حافة التنقل؛ أهداف لمس≥48dp وتسميات AR/EN، Reduced Motion وإيقاف الوميض.

**الخروج المحلي:** ثلاث أصابع عبر InputEventScreenTouch/Drag في Godot؛ UI-camera isolation، الإصبع الرابع، لمس خارج الشاشة، إعدادات/توقف/عودة وتغيير مساحة العرض؛ Windows keyboard/mouse ما زالا يعملان. **الخروج النهائي للهاتف:** APK فعلي، الاتجاه الأفقي، ثلاث أصابع على Hot40Pro؛ لا يُغلق قبل الاختبار المادي. تعذره لا يوقف التصحيحات المحلية.

### الدفعة D — Parkour reliability

- داخل motor الحالي: Vault منخفض، التقاط حافة أثناء الطيران، Hang/Sidle/ClimbUp، إفلات وwall push-off، climbable فقط. كل انتقال له تحقق reach/contact وcapsule sweep وheadroom، ودخول/خروج محدودان لمنع إعادة latch فور الإفلات.
- حافة داخل/خارج حد25cm، طرف جدار وزاوية وميل وledge ضيقة/سقف منخفض؛ لا latch على سطح غير موسوم. مسافة المساعدة هي تصحيح catch فقط، لا قفزة تنقل خلال geometry.
- Moving platforms: استخدام دعم CharacterBody3D/AnimatableBody3D المتاح، مع تحقق platform leave velocity وتثبيت التماس أثناء hang ومقارنة المنصة بدلاً من مقارنة world position فقط. لا parenting عشوائي أو كتابة transform متنافسة.
- فحص المصعد ذهاباً وإياباً، الوقوف والسير والقفز والإفلات عند الأطراف. هدف اختبار أولي: انجراف موضع الراكب بالنسبة لمنصة ترجمة≤2cm خلال60ث في حالة وقوف مستقرة؛ الدوران اختبار مستقل، والرقم ليس نتيجة محققة.

**الخروج:** حالات نجاح وفشل قابلة للإعادة داخل Godot، مع traces/state ومواضع/collision؛ مراجعة جسد/يد/قدم وكاميرا أثناء الفعل. لا اختراق، latch غير مقصود، jitter مرئي أو stuck state. تستخدم الحركات الموجودة فقط؛ أي import ضعيف يذهب مباشرة إلى مهارة Blender، بمحاولتين مبررتين كحد أقصى، دون تغيير Golden/Retarget/Root Motion.

### الدفعة E — الصيانة العمودية والغرف في موضعها السردي

- إعادة استعمال الصيانة ثم بناء route واضح يعلّم climb→hang→gap→elevator ويعيد استعمالها في قرار طريقين. الرئيسي ميسّر، والعلوي أصعب وله ذاكرة اختيارية من المادة السردية المعتمدة، وحفظ اكتشافات ونقطة إعادة قريبة.
- المدخل والمخرج والهدف والمؤشرات جزء من المسار الأصلي، لا مشهد منفصل يُدعى مكتملًا. تستعمل debug fixtures للاختبار فقط.
- بعد نجاح التحكم المحلي والباركور، يبدأ blockout محدود للمنطقة التالية. لا إنتاج كثيف أو قبول G2/G3 للهاتف أثناء غياب القياس؛ يمكن تجهيز الأصول محلياً مع توثيق القيد وفق إذن المالك.
- كل غرفة: مسار قابل للإكمال → أصول فعلية وإضاءة/خامات → تفاعل/صوت/حفظ وأداء. إعادة فحص الكاميرا والتصادم واللمس عند كل تغيير هندسي.

**الخروج:** دخول من الافتتاح، إكمال الطريقين دون مواضع اختبار مجهزة، استعمال المصعد والـgaps، كشف الاختياري مرة واحدة وحفظه، رجوع آمن بعد الفشل واستئناف، AR/EN، ثم انتقال المنطقة التالية دون فقد الحالة.

### الدفعة F — Higgsfield 3D والتكوين الفني

- أصل gameplay يعني مصدر3D/GLB أو مشهد Blender قابل للتحرير فعلاً. الأولوية لمشروع Jutsu الصيانة الموجود، ثم قطع modular/props/أبواب/مختبر من المصدر المناسب.
- خط الأصل: Higgsfield/Jutsu → Blender عند الحاجة → scale بالمتر/pivots/normals/materials/UV/LOD/collision → GLB → Godot → تجربة اللعب والقياس. تسجيل provenance/bounds/triangles/materials/texture sizes/hash ومسار المصدر.
- Seedance2.5/2.0 محفوظان للفيديو/الإخراج حسب السياسة الحالية؛ لا يسمى ناتج فيديو نموذجاً3D. لا إنتاج جماعي قبل قبول غرفة مرجعية داخل المحرك.
- art direction: أنمي نفسي داكن، خامات مرسومة وتظليل ناعم، ضوء يكشف الحواف والهدف والوجه؛ البساطة في الهاتف تخفف الظلال والمؤثرات والخامات وتحتفظ بوضوح اللعب.

**الخروج:** أصل قابل للتفاعل في المشهد الفعلي؛ collision/pivot صحيحان، مواد متسقة، ذاكرة/كلفة رسم مقاسة؛ المقارنة المرئية في Godot، لا لقطة مولدة فقط.

## 4. القياس وإدارة العمل

- قبل كل دفعة: سبب المشكلة، الملفات المحددة، baseline، اختبار الخروج. بعدها: diff scoped، Godot checks، runtime capture/review، self-critique ثم إصلاح وإعادة تحقق وpostflight. يحفظ كل فشل وسبب ثم PASS/FAIL/UNVERIFIED بلا حذف أدلة.
- أول baseline للتحكم: `godot/tests/player_foundation_smoke.gd` و`maintenance_traversal_smoke.gd`؛ تحديثها/add focused regression عند تغير العقد، لا الحفاظ على assertions سلوك DASH القديم بعد إلغائه.
- الأداء: Windows هدف60fps على الجهاز المختبر؛ الهاتف وضع ثابت30fps أساساً و60fps إذا أثبت القياس قدرته. هذه أهداف وليست نتائج. جلسة فعلية20 دقيقة تعطي frame-time/p95/p99/hitches والحرارة والذاكرة، وسجل الدقة/renderer/quality ومسار اللعب؛ recorder المحلي يقيس callbacks ولا يدعي GPU أو touch latency.
- تحفظ Walk والـfixtures ومفاتيح المصدر وسkeleton اللاعب. إصلاح اليد المعزول محفوظ دون export ويستأنف عند حاجة فعلية لحركة/لقطة، لا يؤخر إصلاح التحكم. لا AnimationTree/blending في اختبارات النقل المعزولة.
- بعد نجاح دفعة يبدأ التالي تلقائياً ضمن ترتيب الاعتماد. تعذر دليل خارجي يظل مفتوحاً ويمنع ادعاء قبوله، مع متابعة العمل المستقل الذي سمح به المالك.

## 5. حدود استشارة Antigravity

مصرح به **للاستشارة والنقاش فقط**. لا تعديل ملفات أو تشغيل أو توليد أو commits أو وصول للمفاتيح. لا يفوض له فصل كامل. لم تستخدم استشارة خارجية في إعداد هذه الخطة؛ ظهور نافذة البرنامج ليس إثباتاً لوصول تحكم صالح إليها.

**الإجراء التالي الدقيق:** baseline اللاعب والصيانة، ثم regression يثبت اختلاف سرعة partial/full stick، ثم إصلاح مقدار الحركة وعتبة Run/زر Roll في المسارات الحالية، قبل تطوير الكاميرا أو توسعة الغرف.
